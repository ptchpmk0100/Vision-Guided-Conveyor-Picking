STEP 1 (about 45 min) - problem study, then decide
Question: which real-life problem needs a learned detector? Compare, in half a page, on three points:
what depth already solves, what only RGB can see, how label truth is known by construction in Gazebo.
- Size classes (small/medium/large): depth gives box dimensions, so the network adds little.
- Damaged vs intact: tears, stains, crushed corners, tape are surface cues; depth cannot judge them.
- Both (size and damage): more labels, more data.
Expected outcome: damaged vs intact, classes intact / damaged. Write the decision and reason into this
file or the plan document before step 2. If the study picks something else, stop and ask Khoi.

STEP 2 (about 30 min) - verify the RGB path
RGB is already bridged: /overhead_camera/image (src/twin_action_demo/config/panda_bridge.yaml:74).
  ros2 topic list | sort
  ros2 topic info /overhead_camera/image
  ros2 topic hz /overhead_camera/image
Save one frame, open it, check that a parcel is visible, sharp and about how many pixels wide.
Check whether the gz segmentation camera can be added to the camera sensor without breaking the existing
detector or the frame rate; if not, use entity poses plus projection as the label source.

STEP 3 (about 90 min) - damaged parcels in the sim
Make damage visible as texture/decal variants of the same box (same size, mass and grasp geometry):
a torn corner, a stain, a crushed-corner look. Each variant carries a known condition label by construction
(e.g. a name suffix). Spawn a mixed batch with both conditions and varied order, lighting kept as today.
Check: the arm still picks the variants without change (geometry is identical); the depth detector output is
unchanged (it should not see the damage). Record this as the baseline proof that depth is blind to it.

STEP 4 (about 60 min) - record the dataset
Run Gazebo, record with ros2 bag record --use-sim-time: /overhead_camera/image, /overhead_camera/depth_image,
/overhead_camera/camera_info, /clock, /tf, /tf_static, /joint_states. Add the segmentation/label stream and
the parcel poses as simulation-only ground truth. Vary: parcel order, belt position, yaw, damage variant.
Start with a few hundred labelled frames, hold out whole recordings (not random frames) for evaluation.
Write a dataset manifest: recording names, number of frames per class, git commit, belt speed.

STEP 5 (about 45 min) - export crops and label check   [REVISED 2026-11-11: crop classifier route]
Decision (Khoi, 2026-11-11): the existing depth detector localises parcels; a small image classifier labels
each RGB crop as intact or damaged. No box-detector network is trained.
Extract frames from the recordings. For each frame, project every parcel's ground-truth pose and box size
through camera_info to a pixel box (or use the segmentation camera if step 2 allowed it), cut the crop with
a small margin, and write crops/<split>/<class>/<recording>_<frame>_<parcel>.png. Class comes from the
entity name suffix, never from the depth detector. Also store the crop that the depth detector's own box
would give, so step 7 can measure the real pipeline (depth box -> crop -> classifier), not only
ground-truth crops.
Label check by eye: a contact sheet of about 20 random crops per class; damaged must look damaged, crops
must be centred on the parcel. Also check projection: draw the projected box on 10 full frames.
Check the model's licence (torchvision ResNet18 / MobileNet weights are BSD-style; record the exact weights
licence in the plan). Research and learning project, but the licence must be recorded.

STEP 6 (about 90 min) - train offline
Stop Gazebo first. Separate venv, PyTorch + torchvision, pretrained ResNet18 or MobileNetV3-small,
replace the last layer with 2 outputs (intact, damaged), input 128-224 px, batch 32-64 (crops are small),
mixed precision, light augmentation (brightness, small blur/noise, small shift), TensorBoard.
  python3 -c "import torch; print(torch.cuda.is_available())"
Split by whole recording (train / val / test). Train the head first, then fine-tune all layers at a low
learning rate. Keep one checkpoint per run and the config it used. Expect minutes on the GTX 1650.
If VRAM runs out, lower batch or input size, do not change the dataset to fit.

STEP 7 (about 45 min) - evaluate against ground truth
On the held-out recordings report, per class: precision, recall, and the confusion intact vs damaged.
Compare with the depth detector on the same frames: it should find the parcels but cannot separate the
classes. Only measurements from recordings count; no claim from a single live run.

STEP 8 (about 60 min) - ONNX challenger node (crop classifier)
Export the accepted model to ONNX and add a ROS inference node (CPU or CUDA execution provider) that
subscribes to /overhead_camera/image and the depth detector's parcel detections, crops each parcel from
the RGB image, classifies it, and publishes a separate topic with class and confidence per parcel. Log only; the arm
still reads the depth detector. Check frame rate and latency against the belt speed.

STEP 9 (only if step 7 and 8 pass; about 90 min) - let it drive the arm
Pass condition to start: damaged recall at or above a threshold Khoi agrees on [confirm: number], no
intact parcel sent to reject in the held-out set beyond an agreed rate [confirm: number].
Work to do:
